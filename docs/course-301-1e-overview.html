301.1EDefine · Audit · Plan · AI-assisted software engineering

Turn other people's intent into a plan you can defend.

A practical lab for engineers who receive a PRD, an architecture and a design from other functions, and own the tech spec and the plan that agents will build from.

What participants learn

Move from reading specs to commissioning work.

  • Read product, architecture and design against each other and against the code.
  • Send each gap to the person who owns it, instead of deciding it.
  • Steer an agent to a tech spec that names what is still open.
  • Know what audit and plan run underneath, what is a model's judgment and what is a deterministic check.
Format

Seven stages · 120 minutes

  • Hands-on with SPEED throughout, including its internals
  • Engineers play every role: PM, designer, architect and engineer
  • One brownfield card-payments service and one feature
  • Ends with a verified task plan ready for Execute
The concrete example throughout

A traveller in Tokyo is refused a 2,499 pound television by a rule written at launch, while forty stolen cards are approved across twenty merchants in three minutes. Product, architecture and design have each written their part of the fix. Engineering owns the rest.

Orient → Define → Draft tech spec → Audit → Plan → Verify → Handoff ↖ a gap the audit finds goes back to its owner

The promise to a client

Participants leave able to take a feature from other functions' documents to a verified plan, knowing which parts a person decided, which parts SPEED decided, and which questions are still owned by someone else.

Engineers learn where SPEED grounds itself, which results are a model's judgment, and where it changes their artifacts without asking.

What SPEED grounds itself on

Semantic graphSymbols, references, domain clusters and blast radius across the codebase det
File skeletonsSignatures without bodies, about ten to one. What the Architect actually sees of existing code det
Spec-to-code alignmentEvery code reference in a spec marked confirmed, missing or divergent det
Spec traceabilityEvery requirement matched to a task before the verifier's model runs det

Where SPEED acts without asking

DefineRatifies on the author's behalf when nobody else is eligible
PlanAdds tasks for missed requirements; patches dependencies and re-runs the decomposition gate; reuses cached results while specs are unchanged
VerifyEdits task records in up to three repair cycles

Task size, measured three ways

AuditAbout one developer-day per task; over ten tasks phases the Architect LLM
ArchitectTold to write 15 to 30 minute tasks; not enforced LLM
Decomposition gateLines in the files a task touches; warns above 3,000 det

One feature, five lenses

A real feature touches every function.

Adaptive authorisation was chosen because no single document can be right on its own. Each lens below has an owner, and the engineer meets all of them.

What the client receives
  • A shared language for readiness, ownership and open questions across product, design, architecture and engineering.
  • Seven stage guides grounded in one brownfield payments feature.
  • A visible path from three functions' documents to a verified task plan.
  • Practice telling a model's judgment from a deterministic check, and both from what only a person can see.
  • Engineers who understand what other functions commit to.
What is not promised
  • No audit or plan result is presented as proof the requirements are right.
  • The lab does not set fraud thresholds, risk appetite or legal policy.
  • The lab does not replace the client's own product, design or architecture owners.
  • Execution and approval to ship belong to the courses that follow.

Resulting behaviour

Before commissioning agent work, participants can say what each document decided, what it left open, who owns each open question, what the tools checked, and why the plan says what it says.
